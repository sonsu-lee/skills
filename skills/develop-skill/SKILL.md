# 스킬 개발

요청을 반복 사용에서도 정확하고 안정적으로 수행하는 고품질 스킬로 구현하고, 실제 사례와 검증으로 품질을 입증한다. 품질 기준을 충족한 뒤에만 불필요한 복잡성을 제거한다.

## 품질 계약

- 정확성·완전성·안정성·안전성을 컨텍스트 효율보다 먼저 충족한다. 간결성은 품질이 동등할 때 선택하는 최적화 기준이다.
- 기존 스킬 사용, 개선, 조합, 신규 생성 또는 일회성 처리 중 요구한 결과를 가장 안정적으로 제공하는 형태를 선택한다.
- 모델이 이미 아는 상식보다 프로젝트 고유 절차, 도구 사용법, 실패하기 쉬운 판단을 기록한다.
- 지시의 자유도를 작업 위험에 맞춘다. 판단 작업은 원칙으로, 선호 경로는 의사코드로, 취약하고 반복적인 작업은 스크립트로 고정한다.
- `SKILL.md`에는 품질 기준과 모든 실행에 필요한 핵심 절차를 둔다. 조건부 지식은 `references/`, 결정적 반복 작업은 `scripts/`, 산출물 재료는 `assets/`에 두어 필요한 근거를 빠뜨리지 않으면서 컨텍스트 과부하를 막는다.
- 정적 검증 통과를 행동 품질의 증거로 취급하지 않는다. 트리거와 실제 작업 결과를 별도로 평가한다.
- 고정된 줄 수, 사례 수, 합격률을 보편적 품질 기준으로 사용하지 않는다. 위험도와 결과 분산에 맞춰 평가 강도를 정한다.

## 조건부 참조

- 도메인 지식, 최신 정보, 외부 규격이나 우수 사례가 결과를 좌우하면 [사례와 근거 조사](references/research.md)를 읽고 규칙의 근거와 적용 한계를 정한다.
- 트리거 또는 실제 작업 품질을 평가할 때는 [행동 평가](references/evaluation.md)를 읽고 평가 강도, 기준선, assertion과 홀드아웃을 설계한다.
- 구조를 줄이거나 외부 입력, 네트워크, 파일 쓰기, 셸 명령, 비밀 정보 또는 MCP를 다루면 [품질 보존형 정제와 보안](references/quality-and-security.md)을 읽고 회귀 및 공격성 검사를 수행한다.

## 핵심 워크플로

아래 다섯 단계를 순서대로 수행한다. 적용 조건이 없는 세부 작업은 생략 이유를 남길 수 있지만, 필수 품질 게이트를 시간이나 간결성을 이유로 생략하지 않는다.

### 1. 구현 형태를 판정한다

요청을 다음 중 하나로 분류한다.

- `USE_EXISTING`: 기존 스킬이 요구를 충족한다.
- `IMPROVE_EXISTING`: 기존 스킬을 수정하는 편이 낫다.
- `COMPOSE`: 여러 기존 스킬을 조합하면 된다.
- `CREATE_NEW`: 반복 가능한 독립 기능이 필요하다.
- `NO_SKILL`: 일회성 프롬프트, 프로젝트 지침, 스크립트, 훅 또는 CI가 더 적합하다.

알려진 스킬 루트와 현재 저장소에서 `SKILL.md`를 검색하고 이름이 아니라 기능 용어로 비교한다. 설치 캐시와 소스 저장소를 구분한다. 기존 스킬이 품질 기준을 일부만 충족하면 무리하게 재사용하지 말고 개선, 조합 또는 신규 생성을 선택한다. 기존 스킬의 소스가 확인되면 캐시 사본을 수정하지 않는다.

생성 위치를 사용자가 지정하지 않았다면 현재 저장소의 관례를 따르고, 관례가 없으면 개인 스킬 루트를 사용한다. 대상 호스트와 소스 위치를 확인하기 전에는 파일을 만들거나 수정하지 않는다.

완료 조건: 선택한 구현 형태가 다른 대안보다 요구 품질을 더 잘 충족하는 이유, 기존 스킬로 해결되지 않는 차이, 수정할 소스 위치가 명확하다.

### 2. 작업 계약과 근거를 확정한다

대화와 제공 자료에서 다음을 추출한다.

- 수행할 작업과 제외할 작업
- 대표 사용자 요청과 호출되면 안 되는 근접 요청
- 입력, 출력, 성공 조건과 실패 처리
- 정확성·완전성·안정성·안전성의 필수 품질 기준과 허용할 수 없는 회귀
- 필요한 도구, 외부 시스템, 권한과 대상 호스트
- 생성 위치와 기존 파일 수정 범위
- 오류 비용과 보안 위험

결과를 바꿀 정보만 질문한다. 안전한 기본값으로 진행할 수 있으면 가정을 알리고 계속한다.

도메인 지식이나 최신 외부 정보가 결과를 좌우하면 [사례와 근거 조사](references/research.md)를 적용한다. 공식 규격, 실제 우수 사례, 실패 사례와 반례를 구분하고, 외부 문구나 코드를 재사용할 때는 라이선스와 귀속을 확인한다.

행동을 바꾸려는 스킬이면 대표 사례를 스킬 없이 먼저 실행해 실패, 우회, 불필요한 단계와 결과 변동을 기록한다. 저위험 참조 스킬처럼 기준선의 가치가 낮으면 생략 이유를 남긴다. 기준선 실행에는 기대 답, 의도한 수정이나 이전 결론을 노출하지 않는다.

완료 조건: 대표 성공 사례, 근접 부정 사례, 기대 출력, 필수 품질 기준과 생성 경로가 정해져 있다. 각 비자명한 규칙에 근거가 연결되고, 스킬이 개선해야 할 관찰 가능한 차이 또는 기준선을 생략한 이유가 있다.

### 3. 구조를 설계하고 생성한다

대표 사례를 처음부터 수행한다고 가정하고 반복 실행에 필요한 자원을 선택한다. 파일 수를 줄이기 위해 필요한 근거, 검사 또는 자산을 생략하지 않는다.

- `SKILL.md`: 모든 실행에 필요한 핵심 단계, 분기와 완료 조건
- `references/`: 일부 조건에서만 필요한 지식, 규격과 긴 예시
- `scripts/`: 반복되는 결정적 처리와 검사
- `assets/`: 결과물에 복사하거나 변형할 템플릿과 재료
- `agents/openai.yaml`: Codex UI용 이름, 설명과 기본 호출 예시

새 디렉터리가 필요하면 이 스킬의 경로를 기준으로 스캐폴더를 실행한다.

```bash
python3 "$SKILL_DIR/scripts/scaffold_skill.py" <skill-name> \
  --path <parent-directory> \
  --description "<무엇을 하는지와 언제 사용하는지>" \
  --resources references,scripts
```

스캐폴더는 기본 골격인 `SKILL.md`와 `agents/openai.yaml`을 만들고 선택한 리소스 디렉터리를 추가한다. 기존 대상이 있으면 실행하지 말고 필요한 파일만 수정한다. 기존 파일을 덮어쓰거나 관계없는 사용자 변경을 정리하지 않는다.

참조는 `SKILL.md`에서 한 단계로 연결하고 언제 읽는지 적는다. 같은 의미를 본문과 참조에 중복하지 않는다. 모든 품질 요구를 지시, 참조, 스크립트, 자산 또는 평가 중 하나에 연결한다.

`SKILL.md`를 명령형으로 작성한다. frontmatter의 `description`에는 무엇을 하는지와 언제 호출할지를 함께 적고 한국어·영어·혼합 표현의 핵심 트리거를 포함한다. 호출 후에만 필요한 절차와 판단은 본문에 둔다. 각 주요 단계에는 확인 가능한 완료 조건을 둔다.

추가한 스크립트는 실제로 실행한다. 미완성 표식, 사용하지 않는 예제 파일, 빈 리소스 디렉터리와 작업에 필요하지 않은 보조 문서를 남기지 않는다.

완료 조건: 다른 에이전트가 대화 밖의 숨은 설명 없이 스킬과 제공 자원만으로 대표 작업을 수행할 수 있다.

### 4. 구조와 행동을 검증한다

먼저 이 스킬의 검증기를 실행한다.

```bash
python3 "$SKILL_DIR/scripts/validate_skill.py" <skill-directory>
```

대상 호스트가 제공하는 공식 검증기가 있으면 함께 실행한다. 모든 스크립트의 구문과 대표 실행 경로를 확인한다. 외부 입력이나 시스템 변경을 다루면 [품질 보존형 정제와 보안](references/quality-and-security.md)의 정적·동적 검사를 수행한다.

[행동 평가](references/evaluation.md)를 읽고 표준 평가를 기본값으로 사용한다. 동작이 단순하고 결정적이며 실패 비용이 낮을 때만 빠른 평가로 낮추고 이유를 남긴다. 위험하거나 결과 편차가 큰 스킬은 고신뢰 평가로 강화한다.

직접·간접 긍정 트리거, 근접 부정 트리거, 대표 결과와 홀드아웃을 확인한다. 일반 또는 고위험 스킬은 깨끗한 문맥에서 스킬 적용/미적용 결과를 비교하고, 변동이 크면 반복 실행한다. 객관적 요구는 assertion이나 프로그램 검사로, 주관적 요구는 사전 기준과 사람 검토 또는 블라인드 비교로 판정한다.

완료 조건: 대표 사례와 홀드아웃에서 요구된 정확성·완전성·안정성 기준을 충족하고 트리거·안전성·호환성에 허용되지 않은 회귀가 없다. 기준선을 실행했다면 그 상태에서 선언한 핵심 지표가 기준선보다 개선된다.

### 5. 개선하고 인도한다

검증에 실패하면 원인을 트리거, 지시, 자원, 도구, 환경 또는 평가 결함으로 분류한다. 실패 문구의 키워드를 description에 그대로 붙이지 말고 실패 범주를 일반화한다. 수정 후 원래 실패 사례와 수정에 사용하지 않은 홀드아웃을 다시 실행한다.

[품질 보존형 정제와 보안](references/quality-and-security.md)의 진단을 적용한다.

- 품질 게이트를 먼저 통과한 버전을 기준으로 삼는다.
- 삭제해도 대표 사례와 홀드아웃의 행동이 달라지지 않는 무효 지시를 제거한다.
- 같은 의미의 중복과 오래된 규칙의 침전을 제거한다.
- 조건부 상세 내용은 명확한 참조 지시 뒤로 옮긴다.
- 금지 문구만 있는 지시는 수행할 목표 행동으로 바꾼다.
- 다음 단계 때문에 현재 단계를 서두르면 완료 조건을 강화한다.

수정 후 구조 검증과 영향받는 행동 평가를 다시 실행한다. 정제 전후의 정확성·완전성·안정성·안전성이 동등하거나 향상될 때만 변경을 유지한다.

생성·수정한 파일, 적용한 품질 기준, 실행한 검증과 행동 평가, 회귀 확인 결과와 확인하지 못한 위험을 보고한다. 실행하지 않은 검사를 통과했다고 말하지 않는다. 사용자가 배포나 설치를 요청하지 않았다면 생성된 소스까지만 전달한다.

완료 조건: 품질 게이트와 회귀 검사가 통과하고, 남은 각 문장과 파일이 호출, 판단, 실행 또는 검증 중 하나를 실제로 바꾸며, 사용자가 결과와 남은 불확실성을 확인할 수 있다.
