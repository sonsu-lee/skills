# 스킬 개발

새 스킬 생성과 기존 스킬 수정을 하나의 개발 코어로 수행한다. 둘 다 사용자 목표와 근거를 계약하고, 구조를 설계하고, 실제 행동을 평가하고, 품질을 보존하며 정제한다. 생성은 초기화 방식이 다르고 수정은 기존 계약과 회귀 기준이 추가될 뿐이다.

## 품질 계약

- 정확성·완전성·안정성·안전성을 컨텍스트 효율보다 먼저 충족한다. 간결성은 품질이 동등할 때 선택하는 최적화 기준이다.
- 사용자가 얻을 결과, 필요한 근거, 성공 기준과 중단 조건을 먼저 정의하고 모델이 안전한 실행 경로를 선택할 여지를 남긴다. 절차를 고정해야 결과가 달라지는 경우에만 세부 단계를 의무화한다.
- 하나의 스킬은 하나의 인식 가능한 사용자 목표와 하나의 변경 이유만 가진다. `name`, 제목, `description`, UI 메타데이터, 본문과 모든 번들 자원은 같은 목표 경계를 표현한다.
- 생성과 수정에 같은 품질 게이트를 적용한다. 수정에서는 사용자가 바꾸려는 결과만 변경하고 기존의 유효한 트리거·출력·안전·호환성 계약은 회귀 기준으로 보존한다.
- 기존 스킬 사용·조합·수정, 새 스킬 생성 또는 스킬이 아닌 일회성 처리 중 요구 결과를 가장 안정적으로 제공하는 형태를 선택한다.
- 모델이 이미 아는 상식보다 프로젝트 고유 절차, 도구 사용법, 실패하기 쉬운 판단을 기록한다.
- 지시의 자유도를 작업 위험에 맞춘다. 판단 작업은 원칙으로, 선호 경로는 의사코드로, 취약하고 반복적인 작업은 스크립트로 고정한다.
- `항상`, `절대`, `오직`, `반드시`는 안전·권한·필수 필드처럼 실제 불변 조건에만 사용한다. 검색, 질문, 도구 선택, 반복 여부처럼 맥락에 따른 판단에는 조건과 선택 기준을 적는다.
- `SKILL.md`에는 모든 실행에 필요한 핵심 절차를 두고 조건부 지식은 `references/`, 결정적 반복 작업은 `scripts/`, 산출물 재료는 `assets/`에 둔다.
- 정적 검증 통과를 행동 품질의 증거로 취급하지 않는다. 트리거와 실제 작업 결과를 별도로 평가한다.

## 조건부 참조

- 기존 스킬을 수정·재구성하거나 이름·경계를 바꾸면 [기존 스킬 수정](references/update.md)을 읽고 수정 모드의 세부 절차를 적용한다.
- 도메인 지식, 최신 정보, 외부 규격이나 우수 사례가 결과를 좌우하면 [사례와 근거 조사](references/research.md)를 읽고 규칙의 근거와 적용 한계를 정한다.
- 트리거 또는 실제 작업 품질을 평가할 때는 [행동 평가](references/evaluation.md)를 읽고 평가 강도, 기준선, assertion과 홀드아웃을 설계한다.
- 구조를 줄이거나 결과를 정제하면 [품질 보존형 정제](references/quality.md)를 읽고 품질 회귀를 검사한다.
- Programmatic Tool Calling(PTC)을 명시적으로 다루거나 여러 도구의 대량 구조화 결과를 코드로 축약하는 제한된 단계를 고려하면 [도구 오케스트레이션](references/tool-orchestration.md)을 읽고 직접 호출과 PTC의 경계, 출력 스키마, 중단·재시도와 검증 계약을 정한다.
- 외부 입력, 네트워크, 파일 쓰기, 셸 명령, 비밀 정보 또는 MCP를 다루면 [보안 검토](references/security.md)를 읽고 정적·동적 공격성 검사를 수행한다.

## 핵심 워크플로

아래 다섯 단계를 순서대로 수행한다. `CREATE`, `UPDATE`, `REVIEW`는 같은 코어를 통과하고 각 단계에서 필요한 작업만 분기한다.

### 1. 개발 모드와 권위 있는 소스를 확정한다

요청을 다음 중 하나로 분류한다.

- `USE_EXISTING`: 기존 스킬이 변경 없이 요구를 충족한다.
- `COMPOSE_EXISTING`: 여러 기존 스킬을 조합하면 된다.
- `CREATE`: 반복 가능한 독립 기능을 새 스킬로 만든다.
- `UPDATE`: 기존 스킬의 목표·트리거·행동·자원 또는 검증을 변경한다.
- `REVIEW`: 기존 스킬을 읽기 전용으로 진단하거나 평가한다.
- `NO_SKILL`: 일회성 프롬프트, `AGENTS.md`, 스크립트, 훅, CI 또는 다른 표면이 더 적합하다.

알려진 스킬 루트와 현재 저장소에서 `SKILL.md`를 기능 용어로 검색한다. 이름만으로 동일성을 판단하지 않는다. `UPDATE`에서는 [기존 스킬 수정](references/update.md)에 따라 권위 있는 소스와 영향 범위를 확정한다.

`CREATE`에서는 같은 목표의 기존 스킬이 없는지 확인하고 대상 호스트와 생성 위치를 정한다. `UPDATE`에서는 수정 모드의 소스·보존 계약을 확정한다. `REVIEW`에서는 읽기와 비파괴 검증만 허용하고 파일을 변경하지 않는다.

후보 스킬의 주된 사용자 목표를 결과 중심의 한 문장으로 쓴다. 독립적인 호출 의도, 입력·출력 또는 성공 기준이 둘 이상이면 분리하거나 조합한다. 생성과 수정은 작업 방식이지 별도 사용자 목표가 아니므로 같은 스킬의 모드로 유지한다.

완료 조건: 선택한 모드, 한 문장 목표, 권위 있는 소스와 허용된 변경 범위가 명확하다. `USE_EXISTING`, `COMPOSE_EXISTING`, `NO_SKILL`이면 파일을 변경하지 않고 판정과 다음 경로를 보고한다.

### 2. 작업 계약과 기준선을 확정한다

대화, 대상 스킬과 제공 자료에서 다음을 추출한다.

- 결과 중심의 주된 사용자 목표와 명시적인 비목표
- 수행할 작업, 허용된 변경과 제외할 작업
- 대표 사용자 요청, 호출되면 안 되는 근접 요청과 수정에 사용하지 않을 홀드아웃
- 입력, 출력, 필요한 근거, 성공 조건과 실패·질문·중단 조건
- 정확성·완전성·안정성·안전성의 필수 품질 기준과 허용할 수 없는 회귀
- 필요한 도구, 외부 시스템, 권한과 대상 호스트, 그리고 PTC 후보 단계가 있을 때 직접 호출과 PTC의 경계
- 생성 위치 또는 수정할 소스 파일과 오류 비용

복잡하거나 중요한 요청에는 공식 프롬프트 가이드의 `Goal`, `Success criteria`, `Constraints`, `Tools`, `Output`, `Stop rules`를 점검 렌즈로 사용한다. 모든 항목을 고정 형식으로 강제하지 말고 결과를 바꾸는 정보만 남긴다.

`CREATE`는 스킬이 없는 상태를 기준선으로 삼아 새 스킬이 개선해야 할 차이를 정한다. `UPDATE`는 변경 전 스킬을 기준선으로 삼고 사용자가 고치려는 실패와 유지해야 할 기존 성공을 각각 기록한다. `REVIEW`는 현재 계약과 관찰된 행동을 근거로 판정하고 변경안을 적용하지 않는다.

행동 기준선에는 저자의 기대 답이나 의도한 수정 내용을 노출하지 않는다. 기준선 가치가 낮아 생략하면 이유를 남긴다. 결과를 바꾸지 않는 안전한 기본값은 알리고 진행하며, 중요한 공백만 질문한다.

완료 조건: 대표 성공·근접 부정·홀드아웃 사례, 기대 출력, 변경 가설, 필수 품질 게이트와 보존 계약이 정해져 있다.

### 3. 구조를 설계하고 구현한다

대표 사례를 처음부터 수행한다고 가정하고 반복 실행에 필요한 자원을 선택한다.

- `SKILL.md`: 모든 실행에 필요한 핵심 단계, 분기와 완료 조건
- `references/`: 일부 조건에서만 필요한 지식, 규격과 긴 예시
- `scripts/`: 반복되는 결정적 처리와 검사
- `assets/`: 결과물에 복사하거나 변형할 템플릿과 재료
- `agents/openai.yaml`: UI용 이름, 설명, 기본 호출 예시와 invocation policy
- `evals/`: 트리거, 행동, 회귀와 홀드아웃 사례

`CREATE`에서 새 디렉터리가 필요할 때만 이 스킬의 경로를 기준으로 스캐폴더를 실행한다.

```bash
python3 "$SKILL_DIR/scripts/scaffold_skill.py" <skill-name> \
  --path <parent-directory> \
  --description "<무엇을 하는지와 언제 사용하는지>" \
  --resources references,scripts
```

기존 대상이 있으면 스캐폴더를 실행하지 않는다. `UPDATE`에서는 수정 모드의 변경·마이그레이션 절차를 적용한다. `REVIEW`에서는 이 단계를 설계안과 근거 작성까지만 수행한다.

참조는 `SKILL.md`에서 한 단계로 연결하고 언제 읽는지 적는다. 같은 의미를 본문과 참조에 중복하지 않는다. 각 번들 자원은 주된 목표의 호출, 판단, 실행 또는 검증을 직접 지원해야 한다.

`SKILL.md`를 명령형으로 작성한다. `description`에는 목표와 호출 조건·경계를 간결하게 적고, 절차·출력·안전 판단은 본문에 둔다. PTC 후보 단계가 있으면 [도구 오케스트레이션](references/tool-orchestration.md)에서 판정한 직접 호출·PTC 경계를 구조에 반영한다. 추가하거나 변경한 스크립트는 실제로 실행한다.

완료 조건: 다른 에이전트가 대화 밖의 숨은 설명 없이 스킬과 제공 자원만으로 대표 작업을 수행할 수 있고, 수정 모드에서는 의도하지 않은 계약 변화가 없다.

### 4. 구조와 행동을 검증한다

먼저 이 스킬의 검증기를 실행하고 대상 호스트가 제공하는 공식 검증기가 있으면 함께 실행한다.

```bash
python3 "$SKILL_DIR/scripts/validate_skill.py" <skill-directory>
```

모든 스크립트의 구문과 대표 실행 경로를 확인한다. 외부 입력이나 시스템 변경을 다루면 [보안 검토](references/security.md)의 정적·동적 검사를 수행한다. 이 스킬 자체는 Codex 내장 `skill-creator`와 자연어 트리거가 겹치므로 `agents/openai.yaml`에서 암시적 호출을 끄고 명시적 `$develop-skill` 호출만 평가한다.

[행동 평가](references/evaluation.md)의 모드별 기준선과 표준 평가를 적용한다.

호스트가 암시적 호출을 허용하는 대상에는 직접·간접·불완전 긍정과 근접 부정 트리거를 확인한다. 이 스킬처럼 암시적 호출을 끈 대상에는 명시적 호출과 비호출 경계를 평가한다. PTC를 포함한 스킬은 [도구 오케스트레이션](references/tool-orchestration.md)의 직접 호출 기준선과 두 출력 분리 검사를 추가한다.

완료 조건: 새 목표 사례와 기존 회귀·홀드아웃에서 필수 품질 게이트를 충족하고 트리거·안전성·호환성에 허용되지 않은 회귀가 없다. `REVIEW`에서는 검사한 범위와 미확인 위험이 구분되어 있다.

### 5. 정제하고 인도한다

검증 실패를 트리거, 지시, 자원, 도구, 환경 또는 평가 결함으로 분류하고 근본 원인을 하나씩 수정한다. 실패 문구의 키워드를 `description`에 그대로 붙이지 말고 실패 범주를 일반화한다.

[품질 보존형 정제](references/quality.md)를 적용해 중복, 오래된 규칙, 무효 지시와 불필요한 도구를 한 그룹씩 줄이고 같은 평가를 다시 실행한다. 사용자 결과, 성공·중단 조건, 안전·권한·근거 제약, 도구 라우팅, 필수 출력과 검증 요구는 유지한다.

`UPDATE`에서는 수정 모드의 인도 검사를 적용한다. `REVIEW`에서는 수정하지 않고 발견 사항, 근거, 우선순위와 제안 검증만 보고한다.

생성·수정한 파일, 적용한 품질 기준, 실행한 검증과 행동 평가, 회귀 결과와 미확인 위험을 보고한다. 실행하지 않은 검사를 통과했다고 말하지 않는다. 사용자가 배포·설치를 요청하지 않았다면 권위 있는 소스까지만 변경한다.

완료 조건: 품질 게이트와 회귀 검사가 통과하고, 남은 각 문장과 파일이 호출·판단·실행·검증 중 하나를 실제로 바꾸며, 사용자가 결과와 남은 불확실성을 확인할 수 있다.
