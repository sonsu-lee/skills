# 스킬 개발

바로 만들지 않는다. 기존 스킬이나 더 단순한 방법으로 해결할 수 있는지 먼저 확인하고, 새 스킬이 필요한 경우에만 가장 작은 구조를 만든다.

## 1. 먼저 작업 모드를 고른다

| mode | 선택 기준 |
| --- | --- |
| `USE_EXISTING` | 기존 스킬 하나가 변경 없이 해결한다 |
| `COMPOSE_EXISTING` | 기존 스킬 조합으로 해결한다 |
| `CREATE` | 반복 가능한 독립 목표에 새 스킬이 필요하다 |
| `UPDATE` | 기존 스킬의 목표·트리거·행동·자원·검증을 바꾼다 |
| `REVIEW` | 기존 스킬을 수정하지 않고 진단한다 |
| `NO_SKILL` | 일회성 프롬프트, `AGENTS.md`, 스크립트, hook 또는 CI가 더 적합하다 |

기능 용어로 기존 `SKILL.md`, 사용 가능한 도구와 MCP를 검색한다. 이름이 다르다는 이유로 새 스킬을 만들지 않는다.

`USE_EXISTING`, `COMPOSE_EXISTING`, `NO_SKILL`이면 파일을 만들지 말고 선택한 경로를 보고한다. `REVIEW`이면 읽기와 비파괴 검증만 수행한다.

## 2. 목표와 범위를 한 문장으로 고정한다

다음을 확인한다.

- 사용자가 얻을 결과와 성공 기준
- 스킬이 해야 할 일과 하지 않을 일
- 호출돼야 하는 대표 요청과 호출되면 안 되는 가까운 요청
- 입력, 출력, 필요한 근거, 질문·실패·중단 조건
- 사용할 도구, 외부 시스템, 권한과 변경 가능한 파일
- 유지해야 할 기존 동작과 허용할 수 없는 회귀

독립적인 사용자 목표가 둘이면 스킬을 분리하거나 기존 스킬을 조합한다. 결과를 바꾸지 않는 안전한 기본값은 알리고 진행하고, 중요한 공백만 질문한다.

기존 스킬을 바꾸는 경우에는 [기존 스킬 수정](references/update.md)을 읽고 권위 있는 소스와 회귀 범위를 먼저 확인한다.

## 3. 필요한 파일만 만든다

| 경로 | 넣을 내용 |
| --- | --- |
| `SKILL.md` | 모든 실행에 필요한 핵심 절차와 분기 |
| `references/` | 일부 상황에서만 필요한 긴 규칙·지식·예시 |
| `scripts/` | 반복되고 결정적이어야 하는 처리와 검사 |
| `assets/` | 결과물에 복사하거나 변형할 재료 |
| `agents/openai.yaml` | 사람이 보는 이름·설명·기본 호출과 invocation policy |
| `evals/` | 트리거·행동·회귀·홀드아웃 사례 |

새 디렉터리가 필요한 `CREATE`에서만 scaffold를 실행한다.

```bash
python3 "$SKILL_DIR/scripts/scaffold_skill.py" <skill-name> \
  --path <parent-directory> \
  --description "<무엇을 하는지와 언제 사용하는지>" \
  --title "<한국어 표시 제목>" \
  --short-description "<25~64자의 한국어 기능 요약>" \
  --default-prompt '$<skill-name>을 사용해 <대표 작업>을 수행하고 결과를 검증해줘.' \
  --allow-implicit-invocation false \
  --resources references,scripts
```

기존 디렉터리에는 scaffold를 다시 실행하지 않는다.

## 4. 짧고 실행 가능하게 쓴다

- 하나의 스킬에는 하나의 사용자 목표만 둔다.
- 모델이 이미 아는 상식보다 프로젝트 고유 절차와 실패하기 쉬운 판단을 적는다.
- `SKILL.md`는 명령형으로 쓰고, 조건부 세부사항은 한 단계 아래 reference로 연결한다.
- 같은 규칙을 본문과 reference에 중복하지 않는다.
- 판단 작업은 원칙으로, 선호 경로는 의사코드로, 취약한 반복 작업은 작은 script로 고정한다.
- 이미 있는 도구·MCP·stdlib를 재사용한다. 조사에만 쓴 도구를 대상 스킬의 runtime 의존성으로 복사하지 않는다.
- 사용자가 별도 언어를 지정하지 않으면 본문·description·UI 메타데이터는 한국어를 canonical 원문으로 쓴다. 이름, 경로, schema key와 명령은 ASCII를 유지한다.
- `default_prompt`는 명시적 `$skill-name`과 대표 결과를 담은 한 문장으로 쓴다.
- 암시적 호출은 독립적인 사용자 결과를 소유하고 긍정·부정 트리거 평가를 통과한 스킬에만 허용한다. meta·고영향·명시 전용 스킬은 `false`로 둔다.

조건에 따라 다음 reference만 읽는다.

- 최신 정보·외부 규격·공개 사례가 필요함 → [사례와 근거 조사](references/research.md)
- 트리거·행동·회귀를 평가함 → [행동 평가](references/evaluation.md)
- 구조를 줄이거나 문구를 정제함 → [품질 보존형 정제](references/quality.md)
- PTC 또는 대량 도구 결과를 다룸 → [도구 오케스트레이션](references/tool-orchestration.md)
- 외부 입력·네트워크·쓰기·shell·비밀·MCP를 다룸 → [보안 검토](references/security.md)

## 5. 구조와 실제 행동을 검증한다

기본 검증을 실행한다.

```bash
python3 "$SKILL_DIR/scripts/validate_skill.py" <skill-directory>
```

새 스킬은 UI 메타데이터와 invocation policy까지 strict하게 확인한다. 기존 스킬은 해당 이관이 승인된 경우에만 strict 검사를 적용한다.

```bash
python3 "$SKILL_DIR/scripts/validate_skill.py" <skill-directory> \
  --require-explicit-invocation-policy
```

정적 검증만으로 완료하지 않는다. 대표 성공, 가까운 비호출, 회귀와 홀드아웃에서 실제 결과를 확인한다. 암시적 호출을 끈 스킬은 명시적 호출과 비호출 경계를 평가한다. 추가·변경한 script는 대표 입력으로 실제 실행한다.

## 6. 실패를 고치고 인도한다

실패를 트리거, 지시, 자원, 도구, 환경 또는 평가 문제로 분류하고 공통 원인을 한 곳에서 고친다. 실패 문구를 description에 그대로 덧붙이지 않는다.

중복·낡은 규칙·불필요한 파일을 줄인 뒤 같은 검증을 다시 실행한다. 생성·수정한 파일, 실행한 검증, 회귀 결과와 확인하지 못한 위험을 보고한다. 사용자가 설치·배포를 요청하지 않았다면 권위 있는 소스만 변경한다.

## 경계

- 정확성, 안전, 권한, 데이터 손실 방지와 필수 검증을 간결함 때문에 생략하지 않는다.
- `항상`, `절대`, `반드시`는 실제 불변 조건에만 쓴다.
- 도메인 작업을 대신 수행하거나 완성된 스킬을 설치하는 데 이 스킬을 사용하지 않는다.
- 이 스킬 자체는 명시적 `$develop-skill` 호출만 허용한다.

최종 사용자 응답에는 `present-result`를 마지막 표현 단계로 적용하되, 이 스킬의 판정·근거·권한·ID와 산출물은 바꾸지 않는다.
