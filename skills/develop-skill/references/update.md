## 권위 있는 소스를 찾는다

대상 경로가 설치 캐시, 플러그인 배포물, 복사본 또는 생성 산출물인지 확인한다. 저장소 원본이나 사용자가 지정한 authoring source가 있으면 그 소스를 수정한다. 캐시만 보인다고 캐시를 원본으로 가정하지 않는다.

다음을 읽어 영향 범위를 정한다.

- 대상 `SKILL.md` 전체
- `SKILL.md`가 조건부로 가리키는 관련 참조
- 직접 사용하는 스크립트와 자산
- `agents/openai.yaml`과 invocation policy
- 평가 사례, rubric과 검증기
- 스킬 이름이나 경로를 참조하는 manifest, 문서와 다른 스킬
- 현재 작업 트리의 staged·unstaged·untracked 변경

관계없는 사용자 변경은 수정, 정리, 되돌리기 또는 덮어쓰기 하지 않는다. 권위 있는 소스를 찾지 못하면 캐시를 고치기 전에 사용자에게 소스 또는 설치 갱신 경로가 필요한 이유를 보고한다.

## 변경 전 계약을 고정한다

현재 스킬에서 다음을 추출한다.

```text
user goal
positive and negative triggers
inputs and outputs
success and stop conditions
evidence and safety constraints
tool and permission boundaries
host compatibility
known passing cases
reported failure or desired change
```

사용자가 바꾸려는 항목은 목표 계약으로, 나머지 유효한 항목은 보존 계약으로 표시한다. 기존 문장이 아니라 관찰 가능한 행동을 보존한다. 오래된 구조나 중복 문구를 그대로 유지해야 한다는 뜻으로 해석하지 않는다.

수정 전 버전을 읽을 수 있는 기준선으로 보존한다. Git revision, 임시 복사본 또는 변경 전 파일 내용 중 환경에 맞는 방식을 사용하되 비밀이나 외부 상태를 복제하지 않는다. 평가 실행에는 의도한 수정이나 예상 답을 노출하지 않는다.

## 변경 단위를 설계한다

먼저 관찰된 실패 또는 새 요구를 설명하는 가장 작은 변경 가설을 세운다. 프롬프트, 도구 설명, 참조, 스크립트와 평가를 한꺼번에 바꾸지 말고 원인을 구분할 수 있는 단위로 수정한다.

- `description` 문제: 호출 목표와 긍정·부정 경계를 수정하고 트리거 평가를 다시 실행한다.
- 본문 문제: 결과·성공·중단 조건 또는 실제 판단 규칙을 수정한다.
- 조건부 지식 문제: 상세 내용을 `references/`로 이동하거나 포인터 조건을 고친다.
- 결정적 반복 문제: 필요한 경우에만 `scripts/`로 고정하고 대표 실행을 검증한다.
- 도구 문제: 도구 역할, 입력·출력 필드, 오류와 승인 경계를 명확히 한다.
- 평가 문제: 실제 회귀를 재현하는 사례와 수정에 사용하지 않을 홀드아웃을 추가한다.

중복 지시, 결과 차이가 없는 예시, 모델이 이미 안정적으로 수행하는 일반 절차와 관계없는 도구를 한 그룹씩 줄이고 같은 평가를 다시 실행한다. 짧아졌다는 이유만으로 변경을 유지하지 않는다.

## 구조 변경과 이름 변경을 처리한다

기존 구조가 목표를 흐리거나 생성·수정 같은 작업 모드를 별도 사용자 목표로 잘못 나누면 재구성을 허용한다. 다음 항목을 함께 갱신한다.

- 폴더명과 frontmatter `name`
- H1 제목과 사용자 목표
- `agents/openai.yaml`의 표시 이름, 설명, 기본 프롬프트와 invocation policy
- 로컬 참조와 스크립트 경로
- 평가의 `skill_name`, 명시 호출 이름과 rubric
- README, manifest, 다른 스킬의 링크와 설치·호출 예시

이름 변경은 호출 인터페이스를 바꾸는 호환성 변경이다. 사용자가 구조 변경을 허용했는지 확인하고, 기존 이름을 유지할지 제거할지 결정한다. 호환 alias가 동일 목표를 중복 노출하거나 호출을 불안정하게 만들면 자동으로 만들지 말고 breaking change와 설치 갱신 필요성을 명시한다.

## 변경 전후를 같은 사례로 평가한다

다음 세 집합을 변경 전 버전과 변경본에 동일하게 실행한다.

1. 기존에 성공하던 회귀 사례
2. 새 요구 또는 실패를 재현하는 목표 사례
3. 수정에 사용하지 않은 홀드아웃과 근접 부정 사례

정확성·완전성·안정성·트리거·안전성·호환성 gate를 먼저 비교한다. 목표 사례가 개선되어도 기존 회귀나 홀드아웃이 실패하면 수정 완료로 판정하지 않는다. 품질 gate가 동등하거나 향상된 뒤에만 토큰, 시간, 도구 호출과 유지보수 비용을 비교한다.

파일 목록과 diff를 검사해 허용 범위 밖 변경, 끊어진 참조, 오래된 UI 메타데이터와 미사용 자원을 찾는다. 실행하지 못한 평가, 실제 도구·호스트에서 확인하지 못한 동작과 설치 캐시 미반영 상태를 최종 보고에 남긴다.
