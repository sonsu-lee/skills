# 사례와 근거 조사

도메인 지식이나 최신 외부 정보가 개발할 스킬의 동작을 좌우할 때 이 문서를 읽는다.

## 조사 순서

1. 사용자의 실제 작업과 제공 자료에서 반복되는 입력, 판단, 수정, 출력을 추출한다.
2. 공식 규격과 제품 문서에서 허용된 형식, 현재 동작, 제한 사항을 확인한다.
3. 실제 우수 사례에서 구체적인 행동과 결과를 찾는다.
4. 실패 사례와 반례에서 흔한 오류, 우회, 적용 한계를 찾는다.
5. 사례의 공통점과 차이를 규칙 후보로 정리한다.
6. 이론과 논문은 규칙을 설명하거나 검증하는 데 사용한다.
7. 대표 사례로 규칙을 적용하고, 실패 사례로 잘못된 행동이 차단되는지 확인한다.

## 조사 도구를 선택한다

- OpenAI API, 모델, PTC와 플러그인 규격은 OpenAI Developers MCP의 공식 문서 검색·원문 조회 도구를 우선한다. Codex 자체 동작은 대상 호스트가 제공하는 공식 Codex 문서 경로를 먼저 따르고 필요한 공백만 Developers MCP로 보완한다.
- 공개 저장소의 Agent Skill 구현, 테스트와 유지관리자 코드는 GitHub MCP의 저장소·코드 검색과 파일 조회 도구를 우선한다.
- 검색 결과 목록은 발견 단서로만 취급한다. 규칙을 바꾸는 주장은 선택한 공식 원문이나 저장소 파일을 직접 조회해 확인한다.
- 도구가 없거나 인증·정책으로 사용할 수 없으면 같은 출처를 읽을 수 있는 기존 도구로 대체하고 미확인 범위를 남긴다. 조사 편의를 위해 새 MCP를 만들지 않는다.
- 개발 중 조사에만 사용한 MCP는 생성 대상 스킬의 런타임 의존성이 아니다. 대상 스킬의 대표 작업이 그 MCP 없이는 완료될 수 있을 때만 `agents/openai.yaml`의 `dependencies.tools`에 선언한다.

고정된 여러 읽기 전용 검색을 실행해 URL·저장소·파일 경로를 정규화하고 중복 제거하는 제한된 단계는 [도구 오케스트레이션](tool-orchestration.md)의 PTC 후보로 평가한다. 검색 결과에 따라 다음 질의를 바꾸는 탐색, 관련성 판단, 원문 선택·해석, 인용과 라이선스 확인은 직접 호출로 유지한다.

## 출처 선택

| 주장 | 우선 출처 | 확인할 내용 |
| --- | --- | --- |
| 현재 제품·호스트 동작 | 공식 문서, 릴리스, 소스 저장소 | 버전, 날짜, 지원 범위, 폐기 여부 |
| 파일 형식과 규격 | 공식 사양, 공식 검증기 | 필수 필드, 제한, 호환성 |
| 도메인 절차 | 사용자 자료, 검증된 실무 사례, 공식 지침 | 적용 환경, 실제 결과, 예외 |
| 과학적 효과 | 원 논문, 학회 페이지, 벤치마크 정의 | 비교군, 표본, 지표, 불확실성 |
| 구현 동작 | 유지관리자 코드, 이슈, 테스트 | 실행 버전, 설정, 알려진 실패 |
| 발견 단서 | 검색 결과, 마켓, 블로그, 커뮤니티 글 | 원본 출처로 추적한 뒤 사용 |

검색 엔진과 생성 요약은 발견 도구로만 사용한다. 의사결정을 바꾸는 주장은 원본에서 확인한다. 저장소 전체 스타를 개별 스킬 평판으로 취급하지 않는다.

## 사례 구성

다음 범주에서 필요한 만큼 사례를 만든다. 개수 자체를 품질 점수로 사용하지 않는다.

- 대표 성공 사례
- 표현만 바꾼 변형 사례
- 일부 정보가 빠진 불완전 사례
- 호출되면 안 되는 근접 부정 사례
- 지원 범위를 벗어난 사례
- 공격적이거나 오염된 입력
- 여러 턴에 걸친 사례
- 한국어, 영어, 혼합어 표현

각 규칙에는 가능한 경우 다음을 연결한다.

```text
규칙
├─ 근거: 사용자 요구 / 공식 자료 / 우수 사례 / 관찰된 실패
├─ 적용 조건
├─ 적용하지 않을 조건
└─ 확인 사례
```

## 귀납과 이론의 균형

실제 사례에서 먼저 구체적인 행동을 찾되 실무 사례와 이론을 적대적으로 보지 않는다.

- 사용성, 글쓰기, 운영 절차는 실제 성공·실패 사례에서 구체적인 차이를 찾는다.
- 의료, 법률, 보안, 규격 준수는 공식 지침과 검증된 연구를 우선한다.
- 사례의 성공을 다른 환경에 자동으로 일반화하지 않는다.
- 출처가 약하면 규칙을 영구적 의무가 아니라 평가할 가설로 둔다.

## 신선도와 라이선스

- 현재 동작이 중요한 자료에는 확인 날짜나 버전을 작업 기록에 남긴다.
- 외부 API, 라이브러리, 모델에 의존하면 재평가 조건을 정한다.
- 외부 스킬의 아이디어와 문구를 구분한다. 아이디어를 재구성하고 직접 인용은 최소화한다.
- 재배포할 코드와 문구는 라이선스, 저작권 표시, 귀속 요구를 확인한다.
- 라이선스를 확인할 수 없으면 읽고 비교하는 데만 사용하고 복사하지 않는다.
