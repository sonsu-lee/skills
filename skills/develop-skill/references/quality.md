## 품질의 기준

스킬의 목표는 모든 실행에서 같은 문장을 출력하게 하는 것이 아니다. 필요한 분기와 창의성은 유지하면서 핵심 판단, 작업 순서와 검증을 예측 가능하게 만드는 것이다.

다음 순서로 품질을 판단한다.

1. 정확성과 완전성
2. 안정성과 일반화
3. 트리거 정확도
4. 안전성과 호환성
5. 검증 가능성
6. 유지보수성과 컨텍스트 효율

간결성은 앞선 기준을 희생해 달성하는 목표가 아니다. 대표 사례와 홀드아웃에서 품질이 동등하거나 향상될 때만 구조 정제를 개선으로 인정한다.

## 결과 우선 프롬프트 계약

스킬에는 사용자가 얻을 결과, 필요한 근거, 성공 기준, 제약, 출력과 중단 조건을 먼저 적는다. 세부 절차는 실행 순서가 품질·안전·호환성을 실제로 바꾸는 경우에만 고정한다. 그 밖의 판단에는 보편적 기본값이나 키워드 매핑보다 선택 기준을 주고 모델이 문맥에서 결정하게 한다.

`항상`, `절대`, `오직`, `반드시`는 안전, 권한, 필수 필드와 금지된 부작용처럼 실제 불변 조건에만 사용한다. 검색 여부, 질문 시점, 도구 선택, 반복 횟수 같은 판단에는 적용 조건, 성공·중단 조건과 fallback을 적는다.

현재 동작하는 버전을 기준선으로 두고 다음 항목을 한 그룹씩 제거하거나 수정한 뒤 같은 대표 사례와 홀드아웃을 다시 실행한다.

- 같은 규칙을 반복한 문장
- 행동을 바꾸지 않는 스타일·절차 지시
- 결과 차이가 없는 예시
- 모델이 이미 안정적으로 수행하는 일반 행동의 설명
- 현재 목표와 관계없는 도구와 도구 설명

사용자 결과, 성공·중단 조건, 안전·권한·근거 제약, 맥락에 따른 도구 라우팅, 필수 출력과 검증 요구는 유지한다. 남은 규칙끼리 충돌하는지 검사한다. 더 짧아졌다는 이유만으로 변경을 유지하지 말고 같은 품질 gate를 통과할 때만 채택한다.

## 권한과 응답 경계

개발할 스킬의 요청 유형이 행동 권한을 바꾸면 한곳에서 간결하게 구분한다. 답변·설명·검토·진단·계획 요청에는 읽기와 보고를 허용하되 구현을 자동으로 확장하지 않는다. 변경·생성·수정 요청에는 범위 안의 안전한 로컬 작업과 비파괴 검증을 허용한다. 외부 쓰기, 파괴적 작업, 구매·비용 발생 또는 중대한 범위 확장은 확인 경계로 둔다. 같은 승인 규칙을 여러 단계에서 반복하지 않는다.

길이, 언어와 톤은 제품 요구이거나 측정된 실패를 고칠 때만 구체화한다. `간결하게`, `친절하게` 같은 넓은 표현보다 반드시 보존할 사실·근거·주의사항·다음 행동과 먼저 생략할 반복·배경을 적는다. 언어 전환 조건, 형식과 분량이 결과를 바꾸지 않으면 모델 기본 동작에 맡긴다.

`text.verbosity`, reasoning effort와 pro mode 같은 모델·런타임 설정은 모든 Agent Skill의 공통 규칙으로 복사하지 않는다. 대상 호스트가 지원하고 실제 사용자 결과나 평가 기준에 영향을 줄 때만 해당 환경의 설정으로 명시하고, 같은 대표 사례에서 기본 설정과 비교한다.

## 문장과 구조 진단

| 진단 | 증상 | 조치 |
| --- | --- | --- |
| 조급한 완료 | 완료 여부를 확인하지 않고 다음 단계나 보고로 이동 | 확인 가능한 완료 조건을 추가 |
| 의미 중복 | 같은 규칙이 description, 본문, 참조에 반복 | 단일 출처만 남김 |
| 규칙 침전 | 과거에 필요했던 문장과 예외가 계속 누적 | 현재 사례와 홀드아웃에서 필요성을 확인한 뒤 삭제 |
| 구조적 비대화 | 모든 문장이 유효해도 한 경로에 너무 많은 내용 노출 | 품질을 보존하며 조건부 참조 또는 독립 분기로 분리 |
| 주제 확산 | 이름·제목·description·본문이 서로 다른 사용자 목표를 가리킴 | 주된 목표를 결과 중심의 한 문장으로 다시 쓰고 독립 목표를 별도 스킬로 분리 |
| 참조 범위 이탈 | reference나 다른 번들 자원이 별도 트리거·입력·성공 기준을 가진 작업 절차를 소유 | 독립 절차를 별도 스킬로 옮기고 현재 스킬에는 조합 조건만 남김 |
| 무효 지시 | 삭제해도 기본 모델 행동이 변하지 않음 | 평가로 동등성을 확인한 뒤 삭제하거나 관찰 가능한 행동으로 교체 |
| 부정 지시 | 금지할 행동만 반복해 오히려 활성화 | 수행할 목표 행동과 대안을 먼저 명시 |
| 약한 참조 지시 | 링크는 있지만 언제 읽을지 알 수 없음 | 읽는 조건, 목적, 필요한 결과를 포인터에 명시 |

각 문장을 독립적으로 검사한다.

```text
이 문장이 없으면 에이전트 행동이 달라지는가?
어떤 사례에서 차이가 드러나는가?
그 차이를 평가할 수 있는가?
```

세 질문에 답할 수 없으면 이동, 통합 또는 삭제 후보로 둔다. 변경 후 대표 사례와 홀드아웃을 다시 실행해 품질 회귀가 없을 때만 유지한다.

## 단일 주제 경계

스킬의 주제를 도메인 명사 하나가 아니라 사용자가 얻으려는 결과 하나로 정의한다. `PDF`, `GitHub`, `문서`처럼 넓은 도메인은 그 자체로 단일 주제가 아니다. `PDF 양식 작성`, `PR 리뷰 의견 반영`, `ADR 작성`처럼 호출 이유와 완료 상태를 함께 알아볼 수 있어야 한다.

다음 속성을 공유하면 하나의 목표를 완성하는 단계나 변형으로 볼 수 있다.

- 같은 사용자 호출 의도와 기대 결과
- 호환되는 입력과 출력 계약
- 함께 수행되는 핵심 워크플로
- 같은 완료 조건과 품질 기준
- 함께 변경될 가능성이 높은 규칙과 자원

같은 종류의 산출물에 같은 계약·설계·검증 기준을 적용하는 생성·수정·읽기 전용 검토는 라이프사이클 모드로 함께 둘 수 있다. 이때 공통 코어를 한 번만 정의하고 초기화, 기존 계약 보존과 쓰기 권한만 모드별로 분기한다. 모드마다 별도 품질 체계를 복제하면 서로 다른 규칙이 침전되므로 실패로 본다.

다음 중 하나가 성립하면 독립 스킬로 분리하는 쪽을 기본값으로 둔다.

- 서로 독립적으로 호출하거나 완료할 수 있다.
- 트리거, 필수 입력, 출력 또는 성공 기준이 다르다.
- 한쪽만 별도 권한, 도구, 안전 정책 또는 평가가 필요하다.
- 한쪽의 변경이 다른 쪽의 대표 사례와 무관하다.

`name`, H1 제목, `description`, `agents/openai.yaml`의 `display_name`, `short_description`, `default_prompt`가 같은 목표를 가리키는지 확인한다. 각 reference는 이 목표 안의 한 하위 주제만 설명해야 하며 새 독립 목표를 도입하지 않는다. 여러 독립 목표가 한 사용자 요청에서 필요할 수 있다는 이유만으로 하나의 스킬에 합치지 말고 조합한다.

이 경계는 의미적 속성이므로 정적 검증기의 문자열 규칙만으로 합격을 확정하지 않는다. 대표·근접 부정·경계 밖 사례에서 호출과 결과를 평가하고 사람이 자원별 역할을 검토한다.

## 완료 조건

추상적인 태도 대신 확인 가능한 상태를 적는다.

```markdown
# 약한 지시
결과를 철저히 검토한다.

# 강한 지시
완료하기 전에 생성 파일의 존재, 스크립트 종료 코드,
필수 필드와 대표 사례 결과를 확인한다.
하나라도 확인하지 못하면 완료로 보고하지 않는다.
```

완료 조건은 가능한 범위에서 전체 대상을 포함한다. “문제를 검토한다”보다 “수정한 모든 파일을 검사하고 각 파일의 결과를 기록한다”가 판정하기 쉽다.

## 정보 계층

다음 순서로 정보를 배치한다.

1. `SKILL.md`의 실행 단계: 모든 실행에서 필요한 순서와 완료 조건
2. `SKILL.md`의 핵심 참조: 모든 분기에서 필요한 규칙
3. `references/`: 일부 분기에서만 필요한 상세 지식
4. 외부 공식 자료: 최신성이 필요하고 스킬에 복사하면 곧 낡는 정보

참조 파일 자체보다 포인터 문구가 중요하다.

```markdown
# 약한 포인터
자세한 내용은 references/security.md를 참고한다.

# 강한 포인터
외부 입력을 읽거나 네트워크·파일 쓰기를 수행하면
[보안 검토](references/security.md)를 읽고 공격성 사례를 실행한다.
```

## 주도 개념어

여러 문장에 흩어진 원칙을 모델이 이미 알고 있는 강한 개념 하나로 압축할 수 있다. 다만 멋있어 보이는 용어를 만들지 말고 실제 행동을 안정시키는지 평가한다.

한국어 기술 작업에서는 영어 용어가 더 강하게 작동할 수 있으므로 한국어, 영어, 혼합 표현을 비교한다. 효과가 확인되지 않으면 평범하고 구체적인 완료 조건을 사용한다.

## 호환성

- 대상 호스트의 frontmatter와 도구 이름만 사용한다.
- 특정 호스트의 필드를 다른 호스트의 표준처럼 복사하지 않는다.
- 도구 이름보다 수행할 행동을 설명하고, 호스트별 도구 매핑이 필요하면 조건부 참조로 분리한다.
- 한국어 본문을 기본으로 사용할 수 있지만 description과 평가에는 실제 사용 언어를 반영한다.
- 모델 변경 후 기준선이 달라질 수 있으므로 중요한 스킬은 재평가한다.
