## 품질 게이트

효율이나 간결성을 개선하기 전에 반드시 지켜야 할 품질 기준을 정한다.

| 기준 | 확인할 내용 |
| --- | --- |
| 정확성 | 사실, 계산, 변환과 판단이 요구에 맞는가 |
| 완전성 | 필수 산출물, 단계, 예외와 완료 조건이 빠지지 않았는가 |
| 안정성 | 표현, 언어, 실행 시점이 달라도 중요한 결과가 유지되는가 |
| 트리거 품질 | 필요한 요청에서는 호출되고 근접한 다른 요청에서는 억제되는가 |
| 경계 응집성 | 이름·description·본문과 번들 자원이 하나의 사용자 목표를 지원하며 독립 목표를 섞지 않는가 |
| 안전성·호환성 | 권한, 데이터, 파일과 대상 호스트에 허용되지 않은 회귀가 없는가 |
| 검증 가능성 | 성공과 실패를 결과, assertion, 로그 또는 사람 검토로 판정할 수 있는가 |

각 기준을 필수 게이트와 최적화 지표로 구분한다. 필수 게이트 하나라도 실패하면 토큰, 시간, 파일 수 또는 문장 수의 개선으로 상쇄하지 않는다. 사용자가 품질 간 절충을 명시적으로 승인한 경우에만 예외와 영향을 기록한다.

## 평가 목표를 먼저 정한다

다음 중 스킬이 개선하려는 항목을 명시한다.

- 필요한 상황에서 호출되는가
- 불필요한 상황에서 호출되지 않는가
- 정답률이나 산출물 완성도를 높이는가
- 요구된 작업 과정을 지키는가
- 토큰, 시간, 도구 호출 또는 사용자 개입을 줄이는가
- 반복 실행에서도 안정적인가
- 공격적 입력에서도 안전한가

모든 항목을 동시에 최적화하지 않는다. 필수 품질 게이트, 가장 중요한 개선 목표와 회귀하면 안 되는 항목을 구분한다.

## 평가 단계를 선택한다

### 빠른 평가

동작이 단순하고 결정적이며 실패 비용이 낮은 지시 또는 참조 스킬에만 사용한다. 빠른 평가로 낮춘 이유를 기록한다.

- 대표 작업 수행
- 직접·간접 긍정 트리거
- 근접 부정 트리거
- 정적 검증

### 표준 평가

별도 근거가 없으면 일반적인 생성·변환·워크플로 스킬의 기본값으로 사용한다.

- 빠른 평가 전체
- 생성에서는 스킬 미적용 기준선과 생성본
- 수정에서는 변경 전 버전과 변경본
- 검토에서는 파일 무변경과 진단 근거
- 결정적 assertion
- 수정에 사용하지 않은 홀드아웃
- 결과가 흔들릴 때 반복 실행

### 고신뢰 평가

파일 쓰기, 네트워크, 외부 시스템 변경, 민감 정보, 고비용 작업 또는 주관적 고품질 산출물에 사용한다.

- 표준 평가 전체
- 오염된 입력과 프롬프트 인젝션
- 실패 중간 상태와 복구
- 사람 검토 또는 블라인드 쌍대 비교
- 모델·언어·다중 턴 변형
- 충분한 반복 실행과 분산 확인

## 트리거 평가

다음 범주를 섞어 테스트한다.

| 범주 | 목적 |
| --- | --- |
| 직접 긍정 | 스킬 이름이나 대표 작업을 명시했을 때 호출 |
| 간접 긍정 | 이름 없이 증상과 목적만 표현했을 때 호출 |
| 불완전 긍정 | 일부 정보가 없어도 적절히 호출하고 보완 |
| 근접 부정 | 비슷하지만 다른 작업에서 호출 억제 |
| 경계 밖 독립 목표 | 같은 도메인이어도 트리거·입력·성공 기준이 다른 작업에서 호출 억제 또는 올바른 스킬 조합 |
| 지원 불가 | 범위를 벗어난 요청을 거절하거나 다른 경로 제안 |
| 다국어 | 한국어, 영어, 혼합어에서 호출 차이 확인 |
| 다중 턴 | 앞선 문맥에 의존하는 요청에서 호출 확인 |

긍정 사례를 모델이 스킬 없이도 즉시 처리할 수 있는 한 단계 질문으로만 구성하지 않는다. 실패한 문구의 단어를 description에 그대로 나열하지 말고 공통 의도와 상황을 일반화한다.

## 행동 비교

같은 사례를 깨끗한 문맥에서 개발 모드에 맞는 두 조건으로 실행한다.

- `CREATE`: `without_skill`과 `created_skill`
- `UPDATE`: `before_update`와 `after_update`
- `REVIEW`: 검사 전후 파일 hash와 `review_findings`

수정 평가에는 기존에 성공하던 회귀 사례, 새 요구를 재현하는 목표 사례와 수정에 사용하지 않은 홀드아웃을 모두 포함한다. 새 목표만 개선되고 기존 성공이 깨지면 통과로 판정하지 않는다. 검토 평가는 대상 파일이 바뀌지 않았고 각 발견이 실제 파일·실행 결과와 연결되는지 확인한다.

평가 실행에는 저자의 예상 답, 의도한 수정, 이전 실패 분석을 주지 않는다. 파일, 프롬프트, 출력, 도구 로그와 같은 원시 자료만 제공한다.

다음 표로 결과를 기록한다.

| 사례 | 조건 | 통과 | 과정 위반 | 시간·토큰 | 실패 근거 |
| --- | --- | --- | --- | --- | --- |

## 판정 방법

객관적 요구는 코드나 명령으로 검사한다.

- 필수 파일과 필드 존재
- 출력 스키마
- 종료 코드
- 금지된 변경 부재
- 참조 무결성
- 계산 결과와 결정적 속성

정적 검사는 이름·제목·UI 메타데이터 존재와 참조 무결성 같은 관찰 가능한 속성만 맡긴다. 단일 주제 여부를 단어 일치나 파일명 규칙만으로 판정하지 않는다.

두 조건이 항상 통과하는 assertion은 스킬 기여도를 구분하지 못한다. 제거하거나 사례 난도를 높인다. 빈 출력, 형식만 흉내 낸 출력, 오류 메시지가 우연히 통과하지 않는지 확인한다.

주관적 요구는 명시적인 기준으로 평가한다.

- 기준을 사전에 작성한다.
- 결과의 출처를 가리고 A/B 순서를 바꿔 본다.
- 길고 화려한 결과를 자동으로 우수하다고 판정하지 않는다.
- 일부 결과를 사람이 검토해 평가자 편향을 보정한다.
- 최종 결과뿐 아니라 과정과 도구 사용도 확인한다.
- 주된 사용자 목표를 결과 중심의 한 문장으로 쓰고 각 본문 절차와 번들 자원이 그 목표의 호출, 판단, 실행 또는 검증을 직접 지원하는지 검토한다.
- 별도 트리거·입력·출력·성공 기준을 가진 절차는 독립 목표로 표시하고 분리 또는 조합되지 않았으면 실패로 판정한다.

## 반복과 분산

고정된 반복 횟수를 표준으로 강제하지 않는다.

- 결과가 결정적이고 저위험이면 적은 실행으로 시작한다.
- 결과가 달라지거나 개선 폭이 작으면 반복을 늘린다.
- 평균뿐 아니라 실패 유형과 분산을 함께 본다.
- 단일 성공을 안정성으로 해석하지 않는다.
- 기준선이 이미 안정적으로 성공하면 스킬의 효율 개선 또는 불필요성을 검토한다.

## 개선 루프

1. 실패를 트리거, 지시, 자원, 도구, 환경 또는 평가 결함으로 분류한다.
2. 품질에 가장 큰 영향을 주는 근본 원인을 하나씩 수정한다.
3. 원래 실패 사례와 홀드아웃을 다시 실행한다.
4. 새로운 회귀가 없으면 유지한다.
5. 규칙을 늘려도 개선되지 않으면 설명을 줄이거나 구조를 바꾼다.
6. 실제 사용 중 사용자가 수정한 내용을 새 평가 사례로 추가한다.

평가를 통과시키기 위해 문장을 무조건 늘리거나 줄이지 않는다. 두 버전이 대표 사례와 홀드아웃에서 정확성·완전성·안정성·안전성이 동등할 때만 유지보수 비용과 컨텍스트 사용량이 낮은 쪽을 선택한다.

## 최종 판정

다음을 모두 만족해야 행동 평가를 통과한 것으로 판정한다.

- 대표 사례와 홀드아웃에서 필수 품질 게이트 충족
- 직접·간접 긍정 및 근접 부정 트리거에서 허용 기준 충족
- 생성에서는 선언한 핵심 지표가 미적용 기준선보다 개선
- 수정에서는 새 목표가 개선되고 기존 성공 계약이 변경 전보다 회귀하지 않음
- 검토에서는 파일 무변경과 근거 기반 진단을 모두 충족
- 안전성, 호환성, 필수 과정에 허용되지 않은 회귀 없음
- 실행하지 않은 평가와 남은 불확실성 명시
